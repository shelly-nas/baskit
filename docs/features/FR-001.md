# FR-001: User Authentication & Account Management

## Overview

Baskit is a shopping list app, not a bank. Accounts exist so lists can be synced and shared, and
signing in should happen once per device and then stay out of the way. Security is kept at a
sensible baseline (hashed passwords, rate limiting, account lockout) without the overhead of email
flows, refresh tokens or session management.

Explicitly out of scope:

- Email verification and any other outgoing email
- Password recovery by email (an admin can help a user who forgot their password)
- Refresh tokens, token blacklists and "sign out on all devices"
- Device or session overviews

## 1. Sign-in Required

- **FR-001.1.1**: The app SHALL require an account; there is no signed-out mode and no lists stored
  only on the device
- **FR-001.1.2**: On start the app SHALL check for a stored token and show a loading state while it
  does so
- **FR-001.1.3**: Without a valid token the app SHALL show the sign-in screen, with a switch to
  registration
- **FR-001.1.4**: With a valid token the app SHALL open directly on the main screen
- **FR-001.1.5**: When the server rejects the stored token (expired, account disabled or deleted) the
  app SHALL remove it and return to the sign-in screen
- **FR-001.1.6**: When the server cannot be reached on start the app SHALL keep the stored token and
  show a message with a retry action instead of signing the user out

## 2. Registration

- **FR-001.2.1**: The system SHALL allow users to register with an email address, password and
  display name
- **FR-001.2.2**: The email address SHALL have a valid format and SHALL be unique, compared
  case-insensitively
- **FR-001.2.3**: The password SHALL be at least 8 characters (at most 200); no further complexity
  rules
- **FR-001.2.4**: The display name SHALL be 1 to 100 characters after trimming
- **FR-001.2.5**: A new account SHALL be active immediately and the user SHALL be signed in right
  after registering
- **FR-001.2.6**: Addresses listed in `ADMIN_EMAILS` SHALL get the admin role on registration

Error messages:

- Invalid email → "Enter a valid email address"
- Short password → "Password must be at least 8 characters"
- Email in use → "An account with this email already exists"

## 3. Sign-in and Staying Signed In

- **FR-001.3.1**: The system SHALL provide sign-in with email and password
- **FR-001.3.2**: The system SHALL return the same message for an unknown email and a wrong password:
  "Email or password is incorrect"
- **FR-001.3.3**: A successful sign-in SHALL return one signed token (JWT, HS256) that the app stores
  on the device (`localStorage` on web, SharedPreferences / NSUserDefaults on mobile)
- **FR-001.3.4**: The token SHALL stay valid for `TOKEN_TTL`, default 365 days, so a user who opens
  the app days or weeks later is still signed in
- **FR-001.3.5**: Every request SHALL re-read the user from the database, so disabling or deleting an
  account takes effect immediately despite the long token lifetime
- **FR-001.3.6**: Signing out SHALL remove the token from the device and return to the sign-in
  screen; the server does not track tokens

## 4. Brute-force Protection

- **FR-001.4.1**: The password endpoints SHALL be rate limited per IP address (20 attempts per 15
  minutes)
- **FR-001.4.2**: An account SHALL be locked for 15 minutes after 10 consecutive failed sign-in
  attempts; a successful sign-in resets the counter
- **FR-001.4.3**: A locked account SHALL get the message "Too many failed attempts, try again in 15
  minutes", also when the password is correct

## 5. Account Management

- **FR-001.5.1**: Users SHALL be able to change their display name
- **FR-001.5.2**: Users SHALL be able to change their password by entering the current one
- **FR-001.5.3**: Users SHALL be able to delete their account after confirming with their password;
  this deletes their own lists and removes them from lists shared with them
- **FR-001.5.4**: Admins SHALL be able to list users, change roles and disable or enable accounts; an
  admin cannot remove their own admin access

## 6. API Endpoints

```
POST   /api/auth/register      { email, password, displayName } → { token, user }
POST   /api/auth/login         { email, password }              → { token, user }
GET    /api/auth/me                                             → user
PATCH  /api/auth/me            { displayName?, currentPassword?, newPassword? }
DELETE /api/auth/me            { password }                     → 204
GET    /api/admin/stats
GET    /api/admin/users
PATCH  /api/admin/users/:id    { role?, isActive? }
```

## 7. Possible Later Additions

- Password reset, once the app sends email for another reason
- Sign in with Google / Apple

## 8. Acceptance Criteria

- [ ] The app opens on the sign-in screen without a stored token
- [ ] After signing in, closing the app and opening it two days later shows the main screen without
      signing in again
- [ ] Signing out returns to the sign-in screen
- [ ] A disabled account is sent back to the sign-in screen on its next request
- [ ] Ten wrong passwords in a row lock the account for 15 minutes
- [ ] A user can delete their account and can no longer sign in afterwards
- [ ] No email is sent at any point
