# FR-003: Shopping List Management

## Overview

Shopping list management is the core free-tier capability of Baskit. It allows authenticated users to create, edit, and delete grocery lists, add and remove items via product search, mark items as checked off during a shopping trip, and share lists in real time with household members. The list-service owns this domain; real-time synchronisation for shared lists is delivered via Socket.IO backed by Redis pub/sub.

## 1. List Creation & Types

### 1.1 Requirements

- **FR-003.1.1**: The system SHALL allow an authenticated user to create a shopping list with a name of 1–100 characters
- **FR-003.1.2**: The system SHALL support two list types: `private` (visible only to the owner) and `shared` (visible to the owner and all invited members)
- **FR-003.1.3**: The system SHALL set the list type to `private` by default when no type is specified at creation
- **FR-003.1.4**: The system SHALL allow a user to own a maximum of 50 active shopping lists simultaneously; attempting to create a 51st SHALL return HTTP 422 with body `{"error": "Maximum list limit reached. Please delete an existing list to create a new one"}`
- **FR-003.1.5**: The system SHALL record `created_by` (user ID) and `created_at` timestamp on every list
- **FR-003.1.6**: The system SHALL allow the list owner to change the list name at any time
- **FR-003.1.7**: The system SHALL allow the list owner to change the list type from `private` to `shared` and vice versa at any time
- **FR-003.1.8**: The system SHALL allow the list owner to delete a list, which SHALL soft-delete the list record by setting `deleted_at` to the current timestamp

### 1.2 List Creation Flow

1. User taps "New List" in the list overview screen
2. Flutter client presents a modal with a name field and type selector (Private / Shared)
3. User enters a name and selects the list type
4. Flutter client sends POST request to list-service
5. list-service validates name length and user's current list count
6. list-service creates the list record and returns the new list object
7. Flutter client navigates to the new empty list screen

### 1.3 Error Handling

- Name is empty → "List name cannot be empty"
- Name exceeds 100 characters → "List name must be 100 characters or fewer"
- List limit reached → "Maximum list limit reached. Please delete an existing list to create a new one"
- Service unavailable → "Unable to create list. Please try again"

## 2. Item Management

### 2.1 Requirements

- **FR-003.2.1**: The system SHALL allow any list member (owner or invited collaborator) to add a product to a list by referencing a `product_id` from the product catalogue
- **FR-003.2.2**: The system SHALL allow any list member to add a free-text item when no matching product is found in the catalogue; the item SHALL be stored with `product_id = NULL` and a `free_text_name` field
- **FR-003.2.3**: The system SHALL allow any list member to set a `quantity` (positive integer, minimum 1, maximum 999) and a `unit` (free-text, maximum 20 characters) when adding or editing an item
- **FR-003.2.4**: The system SHALL allow any list member to add a `note` to an item (maximum 200 characters)
- **FR-003.2.5**: The system SHALL prevent duplicate `product_id` entries on the same list; attempting to add an already-present product SHALL return HTTP 422 with body `{"error": "This product is already on your list"}`
- **FR-003.2.6**: The system SHALL allow any list member to update the `quantity`, `unit`, and `note` of an existing item
- **FR-003.2.7**: The system SHALL allow any list member to remove an item from a list (hard delete of the list_items row)
- **FR-003.2.8**: The system SHALL allow any list member to check off an item by setting `is_checked = TRUE`; checked items SHALL remain visible in the list UI in a visually muted state
- **FR-003.2.9**: The system SHALL allow any list member to uncheck a previously checked item by setting `is_checked = FALSE`
- **FR-003.2.10**: The system SHALL allow any list member to permanently remove all checked items from a list in a single bulk-delete operation
- **FR-003.2.11**: The system SHALL support a maximum of 200 items per list; attempting to add a 201st item SHALL return HTTP 422 with body `{"error": "Maximum item limit reached for this list"}`

### 2.2 Add Item Flow

1. User opens a list and taps "Add item"
2. Flutter client presents the product search input (see FR-002)
3. User selects a product from search results or types a free-text item
4. Flutter client presents an optional quantity/unit/note panel
5. User confirms by tapping "Add"
6. Flutter client sends POST request to list-service with `list_id`, `product_id` (or `free_text_name`), `quantity`, `unit`, `note`
7. list-service validates the request and inserts the item
8. For shared lists, list-service publishes an `item_added` event to Redis channel `list:{list_id}`
9. All connected clients for this list receive the `item_added` Socket.IO event and update their local state

### 2.3 Check-Off Flow

1. User taps the checkbox next to an item while shopping
2. Flutter client sends PATCH request to list-service setting `is_checked = TRUE`
3. list-service updates the item and publishes `item_checked` event to Redis channel `list:{list_id}`
4. All connected clients receive the event; the item renders with muted opacity and a strikethrough style

### 2.4 Error Handling

- Duplicate product → "This product is already on your list"
- Item limit reached → "Maximum item limit reached for this list"
- Invalid quantity (not a positive integer) → "Quantity must be a whole number between 1 and 999"
- Note too long → "Note must be 200 characters or fewer"
- Item not found on update/delete → "Item not found"

## 3. List Sharing & Collaboration

### 3.1 Requirements

- **FR-003.3.1**: The system SHALL allow the list owner to invite another registered Baskit user to a shared list by email address
- **FR-003.3.2**: The system SHALL send an email notification to the invited user containing a deep link to accept or decline the invitation
- **FR-003.3.3**: The system SHALL assign invited members the `collaborator` role by default; the `owner` role belongs exclusively to the user who created the list
- **FR-003.3.4**: The system SHALL allow only the list owner to invite members, remove members, and delete the list
- **FR-003.3.5**: The system SHALL allow the list owner to remove any collaborator from a shared list at any time
- **FR-003.3.6**: The system SHALL allow a collaborator to leave a shared list at any time
- **FR-003.3.7**: The system SHALL allow a maximum of 10 members per shared list (1 owner + 9 collaborators); attempting to invite an 11th member SHALL return HTTP 422 with body `{"error": "This list has reached its maximum number of members"}`
- **FR-003.3.8**: The system SHALL display the name and avatar of the member who last modified each item in the list UI
- **FR-003.3.9**: The system SHALL broadcast real-time events to all connected list members within 3 seconds of any list mutation (item added, updated, removed, checked, or unchecked)

### 3.2 Invitation Flow

1. Owner taps "Share list" on a shared-type list
2. Flutter client presents an email input field
3. Owner enters the invitee's email address and taps "Send invite"
4. Flutter client sends POST to list-service invite endpoint
5. list-service validates the email is a registered Baskit user
6. list-service creates a `list_invitations` record with status `pending`
7. list-service publishes an event to notification-service to send the invitation email
8. Invitee opens the deep link and taps "Accept"
9. list-service sets the invitation status to `accepted` and creates a `list_members` record
10. Invitee's Flutter client subscribes to the Socket.IO room for `list:{list_id}`

### 3.3 Real-Time Synchronisation Flow

1. Flutter client connects to list-service WebSocket endpoint on app start
2. list-service authenticates the Socket.IO handshake using the user's JWT
3. Flutter client joins the Socket.IO room for each list the user is a member of
4. On any list mutation, list-service publishes an event to Redis pub/sub channel `list:{list_id}`
5. list-service Socket.IO server subscribes to Redis and broadcasts the event to all room members
6. Flutter clients receive the event and apply optimistic UI update

### 3.4 Conflict Resolution

- **Last-write-wins**: when two members update the same item field within the same second, the mutation with the later server-side timestamp is stored and broadcast
- When a conflict is overwritten, the overwritten member receives a Socket.IO `item_conflict` event; the Flutter client displays a toast: "Your change to [item name] was overridden by [member name]"

### 3.5 Error Handling

- Invitee email not registered → "No Baskit account found with this email address"
- Invitee already a member → "This person is already a member of this list"
- Member limit reached → "This list has reached its maximum number of members"
- Inviting self → "You cannot invite yourself to your own list"
- Collaborator tries to delete list → HTTP 403; client shows "Only the list owner can delete this list"

## 4. List Templates & Recurring Patterns

### 4.1 Requirements

- **FR-003.4.1**: The system SHALL allow a user to save any existing list as a template by copying its current items (product references and quantities) into a named template record
- **FR-003.4.2**: The system SHALL allow a user to create a new list pre-populated with all items from a selected template
- **FR-003.4.3**: The system SHALL allow a user to view, rename, and delete their saved templates
- **FR-003.4.4**: The system SHALL limit each user to a maximum of 20 saved templates; attempting to save a 21st SHALL return HTTP 422 with body `{"error": "Maximum template limit reached. Please delete a template to save a new one"}`
- **FR-003.4.5**: The system SHALL NOT carry over `is_checked` state when creating a list from a template; all items in the new list SHALL have `is_checked = FALSE`

### 4.2 Save Template Flow

1. User opens a list and selects "Save as template" from the list menu
2. Flutter client prompts for a template name (1–100 characters)
3. Flutter client sends POST to list-service template endpoint with `list_id` and `template_name`
4. list-service copies current active (non-deleted) items into a new template record
5. list-service returns the new template object
6. Flutter client confirms: "Template '[name]' saved"

### 4.3 Error Handling

- Template name empty → "Template name cannot be empty"
- Template name too long → "Template name must be 100 characters or fewer"
- Template limit reached → "Maximum template limit reached. Please delete a template to save a new one"

## 5. API Endpoints

### 5.1 List Endpoints

All endpoints require a valid JWT Bearer token in the `Authorization` header.

```
GET    /api/v1/lists
POST   /api/v1/lists
GET    /api/v1/lists/:listId
PUT    /api/v1/lists/:listId
DELETE /api/v1/lists/:listId
```

### 5.2 List Item Endpoints

```
GET    /api/v1/lists/:listId/items
POST   /api/v1/lists/:listId/items
PATCH  /api/v1/lists/:listId/items/:itemId
DELETE /api/v1/lists/:listId/items/:itemId
DELETE /api/v1/lists/:listId/items/checked
PATCH  /api/v1/lists/:listId/items/:itemId/check
PATCH  /api/v1/lists/:listId/items/:itemId/uncheck
```

### 5.3 Sharing & Member Endpoints

```
GET    /api/v1/lists/:listId/members
POST   /api/v1/lists/:listId/invitations
DELETE /api/v1/lists/:listId/members/:memberId
POST   /api/v1/lists/:listId/leave
```

### 5.4 Template Endpoints

```
GET    /api/v1/templates
POST   /api/v1/templates
GET    /api/v1/templates/:templateId
PUT    /api/v1/templates/:templateId
DELETE /api/v1/templates/:templateId
POST   /api/v1/templates/:templateId/create-list
```

### 5.5 WebSocket Events

```
Socket.IO namespace: /lists
Rooms: list:{listId}

Inbound events (client → server):
  join_list    { listId }
  leave_list   { listId }

Outbound events (server → client):
  item_added   { listId, item }
  item_updated { listId, item }
  item_removed { listId, itemId }
  item_checked { listId, itemId, isChecked, updatedBy }
  item_conflict { listId, itemId, winningValue, losingUserId }
  member_joined { listId, member }
  member_left   { listId, memberId }
```

## 6. Database Schema

### 6.1 Lists Table

```sql
lists (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name         VARCHAR(100) NOT NULL,
  type         VARCHAR(10) NOT NULL DEFAULT 'private'
                 CHECK (type IN ('private', 'shared')),
  created_by   UUID NOT NULL REFERENCES users(id),
  created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at   TIMESTAMP NOT NULL DEFAULT NOW(),
  deleted_at   TIMESTAMP
)
```

### 6.2 List Items Table

```sql
list_items (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  list_id        UUID NOT NULL REFERENCES lists(id) ON DELETE CASCADE,
  product_id     UUID REFERENCES products(id),
  free_text_name VARCHAR(255),
  quantity       INTEGER NOT NULL DEFAULT 1 CHECK (quantity BETWEEN 1 AND 999),
  unit           VARCHAR(20),
  note           VARCHAR(200),
  is_checked     BOOLEAN NOT NULL DEFAULT FALSE,
  added_by       UUID NOT NULL REFERENCES users(id),
  last_modified_by UUID NOT NULL REFERENCES users(id),
  created_at     TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at     TIMESTAMP NOT NULL DEFAULT NOW(),
  CONSTRAINT product_or_text CHECK (
    product_id IS NOT NULL OR free_text_name IS NOT NULL
  ),
  CONSTRAINT unique_product_per_list UNIQUE (list_id, product_id)
)
```

### 6.3 List Members Table

```sql
list_members (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  list_id    UUID NOT NULL REFERENCES lists(id) ON DELETE CASCADE,
  user_id    UUID NOT NULL REFERENCES users(id),
  role       VARCHAR(20) NOT NULL DEFAULT 'collaborator'
               CHECK (role IN ('owner', 'collaborator')),
  joined_at  TIMESTAMP NOT NULL DEFAULT NOW(),
  UNIQUE (list_id, user_id)
)
```

### 6.4 List Invitations Table

```sql
list_invitations (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  list_id      UUID NOT NULL REFERENCES lists(id) ON DELETE CASCADE,
  invited_by   UUID NOT NULL REFERENCES users(id),
  invited_email VARCHAR(255) NOT NULL,
  invited_user_id UUID REFERENCES users(id),
  status       VARCHAR(20) NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending', 'accepted', 'declined', 'expired')),
  token        VARCHAR(128) UNIQUE NOT NULL,
  expires_at   TIMESTAMP NOT NULL,
  created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
  responded_at TIMESTAMP
)
```

### 6.5 List Templates Table

```sql
list_templates (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id   UUID NOT NULL REFERENCES users(id),
  name       VARCHAR(100) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMP NOT NULL DEFAULT NOW()
)
```

### 6.6 Template Items Table

```sql
template_items (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  template_id  UUID NOT NULL REFERENCES list_templates(id) ON DELETE CASCADE,
  product_id   UUID REFERENCES products(id),
  free_text_name VARCHAR(255),
  quantity     INTEGER NOT NULL DEFAULT 1 CHECK (quantity BETWEEN 1 AND 999),
  unit         VARCHAR(20),
  CONSTRAINT product_or_text CHECK (
    product_id IS NOT NULL OR free_text_name IS NOT NULL
  )
)
```

### 6.7 Related Tables

- `users`: owner and member references (owned by FR-001)
- `products`: product references in list items (owned by FR-002)

## 7. Security Considerations

### 7.1 Threat Mitigation

- **Unauthorised list access**: Every list endpoint validates that the requesting user is either the owner or an accepted member of the target list; any other user receives HTTP 403
- **Collaborator privilege escalation**: Role is stored server-side in `list_members`; clients cannot self-assign the `owner` role
- **Invitation token forgery**: Invitation tokens are generated using `crypto.randomBytes(64).toString('hex')` (128 hex characters) and expire after 7 days
- **WebSocket room isolation**: Socket.IO room membership is validated server-side on `join_list`; a user can only join rooms for lists they are a member of
- **Item injection**: All free-text fields are stored as parameterized values; no string interpolation into SQL

## 8. Testing Requirements

### 8.1 Unit Tests

- List name validation (empty, too long)
- Item quantity validation (boundary values: 1, 999, 0, 1000)
- Duplicate product check logic
- Template copy logic (items copied, `is_checked` reset to FALSE)
- Conflict resolution timestamp comparison

### 8.2 Integration Tests

- POST `/api/v1/lists` creates a list and returns correct fields
- GET `/api/v1/lists` returns only lists owned or shared with the requesting user
- POST `/api/v1/lists/:listId/items` with duplicate `product_id` returns HTTP 422
- PATCH `/api/v1/lists/:listId/items/:itemId/check` broadcasts `item_checked` event to all room members
- DELETE `/api/v1/lists/:listId/items/checked` removes only checked items
- DELETE `/api/v1/lists/:listId` by a collaborator returns HTTP 403
- Invitation acceptance creates a `list_members` record and removes the invitation `pending` status
- Soft-delete of a list hides it from GET `/api/v1/lists` but retains the database row

### 8.3 Security Tests

- Confirm unauthenticated requests return HTTP 401
- Confirm a user cannot access or mutate another user's private list (HTTP 403)
- Confirm Socket.IO `join_list` is rejected for lists the user is not a member of

## 9. Performance Requirements

- **FR-003.9.1**: GET `/api/v1/lists` SHALL return all user lists within 500ms (95th percentile)
- **FR-003.9.2**: POST `/api/v1/lists/:listId/items` SHALL persist and return the new item within 300ms (95th percentile)
- **FR-003.9.3**: Real-time item events SHALL be broadcast to all connected list members within 3000ms (95th percentile) of the originating mutation
- **FR-003.9.4**: The system SHALL support at least 25 concurrent users connected via Socket.IO without degradation

## 10. Dependencies

- Backend Services: list-service (port 3003), notification-service (port 3007)
- Database: PostgreSQL (lists, list_items, list_members, list_invitations, list_templates, template_items tables)
- Cache / Real-time: Redis (Socket.IO pub/sub, rate limiting)
- External: product-service (product lookup for item addition)
- Auth: user-service (JWT validation via shared middleware)

## 11. Acceptance Criteria

- [ ] A user can create a private list and add items to it
- [ ] A user can create a shared list and invite another registered user by email
- [ ] The invited user receives an email with an accept/decline link
- [ ] After accepting, the invited user can view and edit the shared list
- [ ] Adding an item to a shared list updates the list on all connected members' screens within 3 seconds
- [ ] Checking off an item renders it muted on all connected members' screens within 3 seconds
- [ ] A collaborator cannot delete the list; only the owner can
- [ ] Attempting to add a duplicate product returns an inline error message
- [ ] A user can save a list as a template and create a new list from it
- [ ] Items created from a template have `is_checked = FALSE`
- [ ] Soft-deleted lists do not appear in the list overview
- [ ] A user cannot view or edit another user's private list
