# FR-004: Price Comparison & Analysis

## Overview

Price Comparison & Analysis is a Premium-tier feature that aggregates real-time grocery prices from the six target Dutch supermarket chains, presents per-item and per-list cost comparisons to users, and surfaces active promotions and discounts affecting list items. It is the primary value driver for the €4.99/month subscription and feeds directly into route optimization (FR-005) and savings analytics (FR-011). Free users SHALL see a tasteful upsell prompt when they attempt to access any price comparison view.

## 1. Price Data Aggregation

### 1.1 Requirements

- **FR-004.1.1**: The system SHALL aggregate pricing data from the following Dutch supermarket chains: Albert Heijn, Jumbo, Dirk, Plus, Hoogvliet, and Lidl
- **FR-004.1.2**: The system SHALL store a price record for each combination of `(product_id, store_id, date)`; a new record is inserted each day a scraper run confirms a price, preserving the full price history
- **FR-004.1.3**: The system SHALL record the following fields on each price record: `product_id`, `store_id`, `price_cents` (integer, price in euro-cents), `original_price_cents` (integer, pre-promotion price), `is_on_promotion`, `promotion_label`, `promotion_valid_until`, `scraped_at`
- **FR-004.1.4**: The system SHALL consider the most recent price record per `(product_id, store_id)` pair as the current price for that product at that store
- **FR-004.1.5**: The system SHALL flag a price as stale and exclude it from comparisons when the most recent `scraped_at` for the `(product_id, store_id)` pair is older than 48 hours
- **FR-004.1.6**: The system SHALL expose an internal-only endpoint used by the scraper-service to submit new price batches; this endpoint SHALL NOT be reachable from the public internet
- **FR-004.1.7**: The system SHALL apply anomaly detection: when an incoming price deviates by more than 50% from the previous price for the same `(product_id, store_id)`, the record SHALL be flagged with `needs_review = TRUE` and SHALL NOT be used in price comparisons until a human operator clears the flag

### 1.2 Price Ingestion Flow

1. scraper-service completes a scraping run for one supermarket chain
2. scraper-service sends a POST batch request to the price-service internal endpoint
3. price-service validates each record (required fields, non-negative `price_cents`)
4. price-service applies anomaly detection rule for each price
5. price-service inserts new price records; records flagged `needs_review` are stored but excluded from comparisons
6. price-service invalidates Redis cache keys for affected `(product_id, store_id)` pairs
7. price-service returns a summary: records accepted, flagged, rejected

### 1.3 Error Handling

- Missing required field in batch record → record rejected; remainder of batch continues processing
- `price_cents` is negative or non-integer → "Invalid price value" logged; record rejected
- Price deviation >50% → record stored with `needs_review = TRUE`; not surfaced to users

## 2. Per-Item Price Comparison

### 2.1 Requirements

- **FR-004.2.1**: The system SHALL provide an endpoint that accepts a `product_id` and returns the current price for that product at each store where a non-stale, non-flagged price exists
- **FR-004.2.2**: The system SHALL include the following fields per store in the per-item response: `store_id`, `store_name`, `store_chain`, `price_cents`, `original_price_cents`, `is_on_promotion`, `promotion_label`, `promotion_valid_until`
- **FR-004.2.3**: The system SHALL sort per-item price results by `price_cents` ascending (cheapest first)
- **FR-004.2.4**: The system SHALL return HTTP 200 with an empty `stores` array when no current price data exists for the requested product
- **FR-004.2.5**: The system SHALL gate this endpoint behind Premium subscription check; a request from a Free-tier user SHALL return HTTP 402 with body `{"error": "price_comparison_premium_required", "upgrade_url": "/subscription/upgrade"}`
- **FR-004.2.6**: The system SHALL cache per-item price responses in Redis with a TTL of 30 minutes; cache is invalidated when a new price batch is ingested for the product

### 2.2 Per-Item Price Comparison Flow

1. Premium user taps a product on their shopping list
2. Flutter client sends GET request to price-service per-item endpoint
3. price-service verifies user's `subscription_tier = 'premium'`
4. price-service checks Redis cache; returns cached result on hit
5. On cache miss, price-service queries PostgreSQL for current non-stale, non-flagged prices
6. price-service sorts results cheapest first and writes to Redis cache
7. Flutter client renders a price-per-store comparison card below the product entry

### 2.3 Freemium Upsell Flow (Free User)

1. Free user taps the "Compare prices" affordance on a product
2. Flutter client receives HTTP 402 from price-service
3. Flutter client displays an upsell bottom sheet: "Price comparison is a Baskit Premium feature. Upgrade for €4.99/month to compare prices across Albert Heijn, Jumbo, Dirk, Plus, Hoogvliet, and Lidl." with a "Upgrade to Premium" CTA and a "Not now" dismiss button
4. User taps "Not now" → bottom sheet closes; user remains on the list screen

### 2.4 Error Handling

- Product not found → HTTP 404 with body `{"error": "Product not found"}`
- Free user → HTTP 402 with upsell payload (see FR-004.2.5)
- price-service unavailable → "Price comparison is temporarily unavailable. Please try again"

## 3. Per-List Cost Comparison

### 3.1 Requirements

- **FR-004.3.1**: The system SHALL provide an endpoint that accepts a `list_id` and returns, for each supported store, the total cost of purchasing all catalogue-matched items on the list at that store
- **FR-004.3.2**: The system SHALL calculate the per-store total by summing `price_cents × quantity` for each list item that has a current non-stale, non-flagged price at that store
- **FR-004.3.3**: The system SHALL include in the per-list response: `store_id`, `store_name`, `store_chain`, `total_cents`, `items_priced` (count of items with a price at this store), `items_unavailable` (count of items with no price at this store), `savings_vs_most_expensive_cents`
- **FR-004.3.4**: The system SHALL sort per-list store results by `total_cents` ascending (cheapest first)
- **FR-004.3.5**: The system SHALL flag a store's total as `partial = TRUE` when `items_unavailable > 0`, indicating the total does not cover the full list
- **FR-004.3.6**: The system SHALL gate this endpoint behind Premium subscription check using the same HTTP 402 response defined in FR-004.2.5
- **FR-004.3.7**: The system SHALL complete per-list cost calculation within 5 seconds (95th percentile) for lists of up to 50 items across 6 stores
- **FR-004.3.8**: The system SHALL cache per-list cost responses in Redis with a TTL of 30 minutes; cache is invalidated when the list is modified or when a new price batch affects any product on the list

### 3.2 Per-List Comparison Flow

1. Premium user opens a list and taps "Compare stores"
2. Flutter client sends GET request to price-service list comparison endpoint with `list_id`
3. price-service verifies Premium subscription
4. price-service retrieves all catalogue-matched items from the list
5. price-service fetches current prices for each item at each store
6. price-service aggregates totals per store and calculates `savings_vs_most_expensive_cents`
7. price-service returns sorted store array
8. Flutter client renders a store comparison card showing each store's logo, total, partial flag, and savings badge

### 3.3 Error Handling

- List not found or not owned by requesting user → HTTP 404
- Free user → HTTP 402 with upsell payload
- List contains only free-text items (no `product_id`) → response includes all stores with `total_cents = 0` and `items_unavailable = total items`

## 4. Price History & Trends

### 4.1 Requirements

- **FR-004.4.1**: The system SHALL provide an endpoint that returns the price history for a single `(product_id, store_id)` pair, ordered by date descending, for up to the last 90 days
- **FR-004.4.2**: The system SHALL include the following fields per history record: `date`, `price_cents`, `original_price_cents`, `is_on_promotion`, `promotion_label`
- **FR-004.4.3**: The system SHALL gate this endpoint behind Premium subscription check using the same HTTP 402 response defined in FR-004.2.5
- **FR-004.4.4**: The system SHALL calculate and return the following trend indicators alongside the history array: `avg_price_cents_30d`, `min_price_cents_90d`, `max_price_cents_90d`
- **FR-004.4.5**: The system SHALL retain individual price records for a minimum of 2 years before archiving

### 4.2 Price History Flow

1. Premium user views a product's per-item price comparison
2. User taps "View price history" for a specific store
3. Flutter client sends GET request to price history endpoint with `product_id` and `store_id`
4. price-service returns the 90-day history array and trend indicators
5. Flutter client renders a line chart (using fl_chart package) with promotion periods highlighted

### 4.3 Error Handling

- No history exists for the requested pair → HTTP 200 with empty `history` array and null trend indicators
- Free user → HTTP 402 with upsell payload

## 5. Promotions & Discounts

### 5.1 Requirements

- **FR-004.5.1**: The system SHALL identify a price as a promotion when `price_cents < original_price_cents` in the ingested price record
- **FR-004.5.2**: The system SHALL surface active promotions on list items to Premium users by returning `is_on_promotion = TRUE`, `promotion_label`, and `promotion_valid_until` in all price endpoints
- **FR-004.5.3**: The system SHALL provide an endpoint that returns all active promotions affecting any item on a specified list, available to Premium users only
- **FR-004.5.4**: The system SHALL consider a promotion expired when `promotion_valid_until < NOW()` or when the next scrape for that `(product_id, store_id)` returns `original_price_cents` equal to `price_cents`
- **FR-004.5.5**: The system SHALL display a discount percentage badge on promoted items, calculated as: `ROUND((1 - price_cents / original_price_cents) × 100)`

### 5.2 Promotions Flow

1. Premium user opens a list
2. Flutter client calls GET `/api/v1/prices/lists/:listId/promotions`
3. price-service returns all active promotions on list items
4. Flutter client renders a "Deals on your list" summary section at the top of the list view, showing the store name, discount percentage badge, and promotion label for each promoted item

### 5.3 Error Handling

- List has no promoted items → response returns empty `promotions` array; Flutter client does not render the "Deals on your list" section
- Free user → HTTP 402 with upsell payload

## 6. API Endpoints

### 6.1 Price Comparison Endpoints

All public endpoints require a valid JWT Bearer token. Premium-gated endpoints return HTTP 402 for Free users.

```
GET  /api/v1/prices/products/:productId
GET  /api/v1/prices/lists/:listId
GET  /api/v1/prices/products/:productId/history?storeId={storeId}
GET  /api/v1/prices/lists/:listId/promotions
```

### 6.2 Internal Price Ingestion Endpoint

Requires `X-Internal-Token` header; blocked at Nginx gateway for external requests.

```
POST /api/v1/internal/prices/batch
```

## 7. Database Schema

### 7.1 Stores Table

```sql
stores (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  chain        VARCHAR(50) NOT NULL CHECK (chain IN ('albert_heijn', 'jumbo', 'dirk', 'plus', 'hoogvliet', 'lidl')),
  name         VARCHAR(100) NOT NULL,
  address      VARCHAR(255),
  city         VARCHAR(100),
  postal_code  VARCHAR(10),
  latitude     NUMERIC(9,6),
  longitude    NUMERIC(9,6),
  opening_hours JSONB,
  created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at   TIMESTAMP NOT NULL DEFAULT NOW()
)
```

### 7.2 Prices Table

```sql
prices (
  id                      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id              UUID NOT NULL REFERENCES products(id),
  store_id                UUID NOT NULL REFERENCES stores(id),
  price_cents             INTEGER NOT NULL CHECK (price_cents >= 0),
  original_price_cents    INTEGER NOT NULL CHECK (original_price_cents >= 0),
  is_on_promotion         BOOLEAN NOT NULL DEFAULT FALSE,
  promotion_label         VARCHAR(255),
  promotion_valid_until   DATE,
  needs_review            BOOLEAN NOT NULL DEFAULT FALSE,
  scraped_at              TIMESTAMP NOT NULL DEFAULT NOW(),
  created_at              TIMESTAMP NOT NULL DEFAULT NOW()
)
```

### 7.3 Indexes

```sql
CREATE INDEX idx_prices_product_store ON prices (product_id, store_id);
CREATE INDEX idx_prices_scraped_at ON prices (scraped_at DESC);
CREATE INDEX idx_prices_needs_review ON prices (needs_review) WHERE needs_review = TRUE;
```

### 7.4 Related Tables

- `products`: product references for prices (owned by FR-002)
- `lists` / `list_items`: list references for per-list comparison (owned by FR-003)
- `users`: subscription tier check (owned by FR-001)

## 8. Security Considerations

### 8.1 Threat Mitigation

- **Premium gate bypass**: Subscription tier is read from the JWT claims and cross-validated against the `users` table on every price endpoint request; client-side tier flags are not trusted
- **Internal endpoint exposure**: The `/api/v1/internal/` path prefix is blocked at Nginx; `X-Internal-Token` is a secondary defence at the service level
- **Data integrity**: Anomaly detection prevents scraped data errors from propagating to users; flagged records require manual clearance
- **Cache poisoning**: Redis cache keys are namespaced by `price:product:{product_id}:store:{store_id}` and `price:list:{list_id}`; only price-service writes to these keys via the shared Redis client in `backend/shared/`

## 9. Testing Requirements

### 9.1 Unit Tests

- Anomaly detection: price deviation >50% sets `needs_review = TRUE`
- Stale price filter: records with `scraped_at` older than 48 hours are excluded
- Per-list total calculation: `price_cents × quantity` summed correctly for mixed items
- Savings calculation: `savings_vs_most_expensive_cents` computed correctly
- Discount percentage badge: rounding formula applied correctly

### 9.2 Integration Tests

- POST `/api/v1/internal/prices/batch` persists valid records and rejects invalid ones
- GET `/api/v1/prices/products/:productId` returns stores sorted cheapest first
- GET `/api/v1/prices/lists/:listId` returns `partial = TRUE` for stores missing one or more items
- GET `/api/v1/prices/products/:productId` with a Free-tier JWT returns HTTP 402
- GET `/api/v1/prices/lists/:listId/promotions` returns active promotions only
- Redis cache is populated on first request and returned on second request without a DB query
- Cache is invalidated after a new price batch is ingested for an affected product

### 9.3 Security Tests

- Confirm `/api/v1/internal/` endpoints return HTTP 404 at the Nginx gateway
- Confirm Free-tier user receives HTTP 402 and upsell payload on every Premium-gated endpoint
- Confirm a user cannot retrieve price comparisons for a list they do not own

## 10. Performance Requirements

- **FR-004.10.1**: Per-item price comparison SHALL return results within 500ms (95th percentile) for a cached response
- **FR-004.10.2**: Per-item price comparison SHALL return results within 2000ms (95th percentile) for an uncached response
- **FR-004.10.3**: Per-list cost comparison SHALL complete within 5000ms (95th percentile) for a list of 50 items across 6 stores
- **FR-004.10.4**: Price history retrieval (90 days) SHALL complete within 1000ms (95th percentile)
- **FR-004.10.5**: Internal batch ingestion endpoint SHALL process a batch of 10,000 price records within 30 seconds

## 11. Dependencies

- Backend Services: price-service (port 3004), store-service (port 3005)
- Database: PostgreSQL (prices, stores tables)
- Cache: Redis (price comparison cache, TTL 30 minutes)
- Internal: scraper-service (price data ingestion)
- Auth: user-service (JWT validation, subscription tier)

## 12. Acceptance Criteria

- [ ] A Premium user viewing a product sees current prices from all stores that carry it, sorted cheapest first
- [ ] A Free user tapping "Compare prices" sees the upsell bottom sheet and is not shown any price data
- [ ] A Premium user on a list sees total cost per store and which stores have the full list vs a partial match
- [ ] A store with a price older than 48 hours is excluded from all comparisons
- [ ] A price record that deviates by more than 50% from the previous price is flagged and not shown to users
- [ ] Active promotions on list items are surfaced in the "Deals on your list" section for Premium users
- [ ] Discount percentage badges are calculated correctly and displayed on promoted items
- [ ] Per-item price comparison is served from Redis cache within 500ms on repeat requests
- [ ] The internal batch ingestion endpoint is inaccessible from the public internet
- [ ] Price history for 90 days is retrievable per product per store for Premium users
