# FR-002: Product Search & AI Matching

> **Status:** target specification. Implementation details (services, tables, endpoints) were written
> for the earlier microservice design; the current architecture is described in `CLAUDE.md`.
> Offer and price data come from the supermarket-scraper public API.

## Overview

This feature provides the product search and intelligent matching capability that underpins every user interaction with grocery items in Baskit. Free users access basic text search and autocomplete; the AI-powered vector-similarity matching that maps generic terms to specific branded products across Dutch supermarket chains is available to all tiers because accurate product identification is a prerequisite for list management, price comparison, and route optimization.

## 1. Basic Product Search

### 1.1 Requirements

- **FR-002.1.1**: The system SHALL provide a text-based product search endpoint that accepts a query string and returns matching products from the Baskit product catalogue
- **FR-002.1.2**: The system SHALL return search results within 2 seconds (95th percentile) for queries against a catalogue of up to 500,000 products
- **FR-002.1.3**: The system SHALL return a maximum of 50 results per search request, ordered by relevance score descending
- **FR-002.1.4**: The system SHALL support Dutch-language search terms as the primary input language
- **FR-002.1.5**: The system SHALL perform case-insensitive matching on product names, brands, and EAN barcodes
- **FR-002.1.6**: The system SHALL include the following fields in every search result item: `product_id`, `name`, `brand`, `size_quantity`, `size_unit`, `category_id`, `category_name`, `image_url`, `ean`
- **FR-002.1.7**: The system SHALL filter search results to only include products whose `status` is `active`
- **FR-002.1.8**: The system SHALL support barcode (EAN-13) lookup as a search mode, returning the single matching product or an empty result set

### 1.2 Search Flow

1. User types one or more characters into the product search field
2. Flutter client debounces input for 300 milliseconds
3. Client sends GET request to product-service with query parameter `q`
4. product-service performs full-text search against the products catalogue
5. product-service ranks results by text-match relevance score
6. product-service returns paginated JSON array of matching products
7. Flutter client renders results in a scrollable list below the search field
8. User selects a product from the results to add it to the active list or view its detail

### 1.3 Error Handling

- Query string shorter than 1 character → client suppresses the request; no error displayed
- Query string longer than 200 characters → "Search query is too long"
- product-service unavailable → "Product search is temporarily unavailable. Please try again"
- No results found → "No products found for '[query]'. Try a different search term"

## 2. Autocomplete & Suggestions

### 2.1 Requirements

- **FR-002.2.1**: The system SHALL provide an autocomplete endpoint that returns up to 10 product name suggestions for partial input of 2 or more characters
- **FR-002.2.2**: The system SHALL return autocomplete suggestions within 500ms (95th percentile)
- **FR-002.2.3**: The system SHALL rank autocomplete suggestions by a combination of text-match score and global product popularity (measured by add-to-list frequency across all users, anonymised)
- **FR-002.2.4**: The system SHALL surface the user's own previously added products at the top of autocomplete results when they match the query, before globally ranked suggestions
- **FR-002.2.5**: The system SHALL NOT include products with `status` other than `active` in autocomplete suggestions

### 2.2 Autocomplete Flow

1. User types 2 or more characters
2. Flutter client sends debounced GET request to the autocomplete endpoint
3. product-service queries a pre-built autocomplete index
4. product-service prepends any matching products from the user's own list history
5. product-service returns up to 10 suggestions
6. Flutter client renders inline suggestion dropdown
7. User taps a suggestion to complete the search or add directly to the list

### 2.3 Error Handling

- Autocomplete endpoint unavailable → client silently falls back to full search; no error shown to the user
- Input below 2 characters → client suppresses autocomplete request; no error displayed

## 3. AI-Powered Product Matching

### 3.1 Requirements

- **FR-002.3.1**: The system SHALL implement vector-similarity matching that maps a user-entered generic term (e.g., "peanut butter") to one or more specific branded products in the catalogue (e.g., "Calvé Pindakaas Romig 350g")
- **FR-002.3.2**: The system SHALL return AI-matched candidates ranked by semantic similarity score, highest first
- **FR-002.3.3**: The system SHALL return a maximum of 5 AI-matched candidates per generic term
- **FR-002.3.4**: The system SHALL complete AI matching within 3 seconds (95th percentile) when the vector index contains up to 500,000 product embeddings
- **FR-002.3.5**: The system SHALL include a `match_confidence` field (float, 0.0–1.0) in each AI-matched result
- **FR-002.3.6**: The system SHALL only surface AI-matched candidates with `match_confidence` ≥ 0.60
- **FR-002.3.7**: The system SHALL fall back to standard full-text search results when AI matching returns zero candidates above the confidence threshold
- **FR-002.3.8**: The system SHALL store product embeddings in a vector database (Pinecone or Weaviate) and refresh embeddings when product catalogue records are updated
- **FR-002.3.9**: The system SHALL allow the user to reject an AI-matched suggestion and search manually; the rejection SHALL be recorded to improve future matching

### 3.2 AI Matching Flow

1. User enters a generic term in the product search field
2. product-service detects that the query does not match any product name exactly
3. product-service converts the query to a vector embedding using OpenAI Embeddings API
4. product-service queries the vector database for the nearest neighbours
5. product-service filters candidates to `match_confidence` ≥ 0.60
6. product-service merges AI candidates (ranked first) with standard text-search results
7. Flutter client renders AI candidates with a "Best match" label and confidence badge
8. User selects a product or rejects all AI candidates and refines the query

### 3.3 Error Handling

- OpenAI Embeddings API unavailable → system falls back to text-only search silently; no error shown
- Vector database unavailable → system falls back to text-only search silently; no error shown
- All AI candidates below confidence threshold → system shows text-search results without "Best match" label

## 4. Product Detail

### 4.1 Requirements

- **FR-002.4.1**: The system SHALL provide a product detail endpoint that returns full metadata for a single product identified by `product_id`
- **FR-002.4.2**: The system SHALL include the following fields in the product detail response: `product_id`, `name`, `brand`, `description`, `size_quantity`, `size_unit`, `category_id`, `category_name`, `image_url`, `ean`, `status`, `created_at`, `updated_at`
- **FR-002.4.3**: The system SHALL return HTTP 404 with body `{"error": "Product not found"}` when the requested `product_id` does not exist
- **FR-002.4.4**: The system SHALL return HTTP 404 with body `{"error": "Product not found"}` when the requested product has `status` other than `active`

### 4.2 Product Detail Flow

1. User taps a product in search results
2. Flutter client sends GET request to product detail endpoint with `product_id`
3. product-service retrieves full product record from PostgreSQL
4. product-service returns product detail JSON
5. Flutter client renders product detail screen with name, brand, size, image, and category
6. User can add the product to a list directly from the detail screen

### 4.3 Error Handling

- Product not found → "This product is no longer available"

## 5. Product Catalogue Management

### 5.1 Requirements

- **FR-002.5.1**: The system SHALL maintain a product catalogue seeded from scraper-service output and manual imports
- **FR-002.5.2**: The system SHALL deduplicate products by EAN when ingesting new catalogue data; an existing record with the same EAN SHALL be updated, not duplicated
- **FR-002.5.3**: The system SHALL soft-delete products by setting `status = 'inactive'` rather than deleting rows, preserving referential integrity with list items and price history
- **FR-002.5.4**: The system SHALL expose an internal (service-to-service, not user-facing) endpoint for bulk catalogue upsert used by the scraper-service

## 6. API Endpoints

### 6.1 Product Search Endpoints

All endpoints require a valid JWT Bearer token in the `Authorization` header unless noted otherwise.

```
GET  /api/v1/products/search?q={query}&page={page}&limit={limit}
GET  /api/v1/products/autocomplete?q={query}
GET  /api/v1/products/ai-match?q={query}
GET  /api/v1/products/:productId
GET  /api/v1/products/barcode/:ean
```

### 6.2 Internal Catalogue Endpoints

Requires internal service authentication (shared secret header `X-Internal-Token`), not exposed through the API gateway to the public internet.

```
POST /api/v1/internal/products/upsert-bulk
```

## 7. Database Schema

### 7.1 Products Table

```sql
products (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  ean           VARCHAR(13) UNIQUE,
  name          VARCHAR(255) NOT NULL,
  brand         VARCHAR(100),
  description   TEXT,
  size_quantity NUMERIC(10,3),
  size_unit     VARCHAR(20),
  category_id   UUID REFERENCES categories(id),
  image_url     VARCHAR(500),
  status        VARCHAR(20) NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active', 'inactive')),
  embedding_id  VARCHAR(100),
  created_at    TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMP NOT NULL DEFAULT NOW()
)
```

### 7.2 Categories Table

```sql
categories (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        VARCHAR(100) NOT NULL,
  parent_id   UUID REFERENCES categories(id),
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  TIMESTAMP NOT NULL DEFAULT NOW()
)
```

### 7.3 Related Tables

- `prices`: stores current and historical prices per product per store (owned by FR-004)
- `list_items`: references `products.id` for items added to shopping lists (owned by FR-003)

## 8. Security Considerations

### 8.1 Threat Mitigation

- **Enumeration via product IDs**: UUIDs are used instead of sequential integers to prevent catalogue enumeration
- **Search injection**: All query parameters are passed as parameterized values; no string interpolation into SQL
- **Rate limiting**: Search and autocomplete endpoints are rate-limited to 60 requests per minute per authenticated user via shared rate-limit middleware in `backend/shared/`
- **Internal endpoint exposure**: The `/api/v1/internal/` path prefix is blocked at the Nginx gateway level and requires `X-Internal-Token` at the service level

## 9. Testing Requirements

### 9.1 Unit Tests

- Full-text search relevance ranking logic
- Autocomplete index query and result merging
- AI confidence threshold filtering
- EAN deduplication logic on bulk upsert
- Product field validation on creation

### 9.2 Integration Tests

- GET `/api/v1/products/search` returns correct results for Dutch-language queries
- GET `/api/v1/products/autocomplete` returns user history results before global results
- GET `/api/v1/products/:productId` returns 404 for inactive products
- GET `/api/v1/products/barcode/:ean` returns the correct product for a valid EAN
- AI matching fallback triggers correctly when vector DB is unavailable
- Bulk upsert deduplicates by EAN and does not create duplicate rows

### 9.3 Security Tests

- Confirm `/api/v1/internal/` endpoints return 404 at the Nginx gateway
- Confirm search endpoint rejects requests without a valid JWT
- Confirm rate limiting returns HTTP 429 after 60 requests per minute

## 10. Performance Requirements

- **FR-002.10.1**: Product text search SHALL return results within 2000ms (95th percentile)
- **FR-002.10.2**: Autocomplete SHALL return suggestions within 500ms (95th percentile)
- **FR-002.10.3**: AI matching SHALL return candidates within 3000ms (95th percentile)
- **FR-002.10.4**: Product detail retrieval SHALL complete within 200ms (95th percentile)
- **FR-002.10.5**: Bulk catalogue upsert SHALL process at a minimum rate of 1,000 products per second

## 11. Dependencies

- Backend Services: product-service (port 3002)
- Database: PostgreSQL (products, categories tables)
- Cache: Redis (autocomplete index, rate limiting)
- External: OpenAI Embeddings API (AI matching)
- External: Pinecone or Weaviate (vector database for embeddings)
- Internal: scraper-service (catalogue data source)

## 12. Acceptance Criteria

- [ ] A search for a Dutch product name returns relevant results within 2 seconds
- [ ] A search for an EAN barcode returns the correct single product
- [ ] Autocomplete suggestions appear after typing 2 characters
- [ ] The user's previously added products appear at the top of autocomplete results when they match
- [ ] A generic query (e.g., "pindakaas") surfaces AI-matched branded products with a "Best match" label
- [ ] AI candidates with confidence below 0.60 are not displayed
- [ ] When OpenAI or the vector DB is unavailable, text search results are shown without error to the user
- [ ] Requesting a non-existent or inactive product ID returns HTTP 404
- [ ] Bulk upsert does not create duplicate EAN entries in the products table
- [ ] Search endpoint returns HTTP 429 after 60 requests per minute from one user
- [ ] Internal catalogue endpoints are inaccessible from the public internet
